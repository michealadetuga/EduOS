Secondary School E-Learning Platform
 Discussion Document - For Review Before Development Begins
This document is meant to be read and discussed together before any development starts. It lays out the full
shape of the project as currently understood, including open questions that still need to be talked through.
Background
This project began as a university-focused E-Learning Management System ("Redesign and
Implementation of E-Learning Management System"), covering course registration, attendance
tracking, automated emails, a quiz module, digital library, past questions repository, assignment
module, virtual classes, and institutional email auto-generation. That system was hosted on Vercel,
Render, and MongoDB Atlas.
We are now extending the concept to serve secondary schools as well. This is a deliberate shift in
direction: rather than building for one specific school, the secondary school version is being designed
as a multi-tenant platform that any secondary school can sign up for and use independently, on shared
infrastructure.

Platform Model: Multi-Tenant, Self-Service
Any secondary school will be able to register on the platform and begin using it immediately, without
needing manual approval. Each school's data (classes, subjects, teachers, students, parents, results) is
kept fully isolated from every other school on the platform.
●
Self-service signup - a school registers itself and is instantly active.
●
Each school is assigned a unique school identifier used to scope all of its data.
●
Email verification confirms the registering contact before first login.
●
The first person to register a school automatically becomes that school's Admin.
●
No cross-school visibility - one school can never see another school's data.

Module 1: Super Admin (Platform Level)
●
Dashboard: total schools, total users, recent signups, activity trends.
●
School directory: list and search all registered schools, view status (active/suspended).
●
Suspend or reactivate a school account.
●
Optional: view-only access into a school's data for support purposes.
●
Optional: platform-wide announcements to all School Admins.
Module 2: School Signup & Onboarding
●
Public registration form: school name, address, contact email, phone, school type.
●
Auto-generated unique school ID created on signup, used to scope all future data.
●
Email verification required before first login.
●
First registrant is automatically granted the School Admin role.
●
Onboarding checklist shown on first login: set up classes, add subjects, add teachers, add students.
Module 3: School Admin (Per-School Level)
School Profile
●
School name, logo, address, contact info.
●
Academic session/term settings (e.g., 2026/2027, First/Second/Third Term).
Class & Arm Management
●
Class name (e.g., JSS1, SS2), arm (A, B, Science, Art).
●
Class teacher assignment and student capacity.
●
Create, edit, and delete classes and arms per session.
Subject Management
●
Subject name, subject code, assigned class(es) and teacher(s).
●
Core vs. elective subject flag for SS tracks (Science, Art, Commercial).
Teacher Management
●
Full name, email, phone, assigned subjects and classes, employment status.
●
Admin creates teacher accounts; login credentials sent by email.
Student Management
●
Full name, admission number (auto-generated), class/arm, admission date, gender, linked
parent/guardian.
●
Bulk upload via CSV for adding many students at once.
●
Promotion/repeat action at the end of term or session.
Parent/Guardian Linking
●
Full name, email, phone, linked student(s).
●
One parent account can link to multiple children within the same school.

=== Page 5 ===
Result / Report Card Oversight
●
Admin reviews and approves results entered by teachers before release.
●
Report card template settings: school logo, grading scale, comments section.
Communication
●
Announcements visible only to that school's own teachers, students, and parents.
●
Automated email triggers, e.g. account creation, result release.
Critical requirement: every record - class, subject, student, teacher, parent, result - must be scoped to its
owning school's ID. No school should ever be able to view or access another school's data, with the sole
exception of Super Admin oversight access.

=== Page 9 ===
Infrastructure
The platform will build on the same free-tier stack used for the university system: Vercel for hosting the
frontend, Render for backend services, and MongoDB Atlas for the database. Whether this is a new
codebase/repository or an extension of the existing one is an open question below.
Ideas to Consider (Open for Discussion)
A few suggestions worth discussing as the build progresses - none of these are decided yet, just
flagged for your input:
●
Subscription/pricing tiers for schools (e.g., free tier with limits, paid tier for larger schools) if this is
meant to be commercially sustainable.
●
A super admin support-access mode, so issues can be diagnosed for a school without needing their
login.
●
Audit logging on admin actions (who created/edited/deleted a record), useful once multiple schools
and staff are on the platform.
●
Whether this is a new codebase/repository or an extension of the existing university system's
codebase.
●
Starting Phase 1 with a single pilot school's data even though the architecture is multi-tenant from day
one, to validate the flow before opening signup publicly.
●
A rough timeline/effort estimate per phase, once scope is agreed - not fixed dates, just a sense of
scale.
